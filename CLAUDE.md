# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repository.

## What this is

Baltic Road Atlas is an iOS road-intelligence app for Latvia, Lithuania, and Estonia.
It answers "is this road worth driving?" — surface type, condition, camper-friendliness,
overnight parking, water/toilets, and historical points of interest — rather than
competing with Google/Apple Maps on turn-by-turn navigation. Full product vision lives
in [README.md](README.md).

## Guiding principle

The app is a road intelligence companion, not a navigator replacement. When a feature
request is ambiguous, prefer the interpretation that helps someone decide _which_ road
to take or _what's nearby_, over one that duplicates existing turn-by-turn nav.

## Current phase

**Phase 2 — real iOS app target exists.** Xcode is installed (M4 Mac, no disk space
constraint) and an iOS Simulator runtime is downloaded. The core engine
(`SharedModels`, `OSMClient`, `RoadScoring`, `CamperEngine`, `HistoricalRoutes`,
`MapFeature`) is still plain Swift Package Manager libraries — that hasn't changed and
shouldn't. What's new is `BalticRoadAtlasApp/`: a real iOS app target that imports
those packages and runs on the Simulator, generated via
[XcodeGen](https://github.com/yonaskolb/XcodeGen) from `BalticRoadAtlasApp/project.yml`
rather than a hand-edited `.xcodeproj`.

`BalticRoadAtlasApp/project.yml` is the source of truth for the Xcode project, not the
generated `BalticRoadAtlasApp.xcodeproj` itself — if you change target settings,
dependencies, or Info.plist keys, edit `project.yml` and regenerate:

```bash
cd BalticRoadAtlasApp && xcodegen generate
```

The `.xcodeproj` is still committed (so the project opens immediately without anyone
needing XcodeGen installed just to browse it), but treat hand-edits to it as
disposable — they're overwritten the next time someone runs `xcodegen generate`.

`BalticRoadAtlasCLI` and `BalticRoadAtlasPreview` (the macOS-window preview host) both
still work and remain useful for fast iteration without booting the Simulator — prefer
them for quick logic/layout checks, use the real app target when you need actual iOS
behavior (real chrome, touch gestures, on-device quirks, permissions prompts).

## Roadmap

1. **Core engine** — package structure, shared models, road scoring, OSM client,
   Baltic Way dataset. Ongoing — new domain logic keeps landing here as features need it.
2. **iOS app shell** _(current)_ — real iOS app target (`BalticRoadAtlasApp/`) exists
   and runs on Simulator; map view is wired in but doesn't render real road data yet
   (`MapFeature` → `OSMClient` isn't connected — see GitHub issue #15).
3. **Feature build-out** — Camper mode, historical routes, parking, community reports.
4. **Backend** — Supabase: auth, accounts, saved routes, favorites, crowdsourced reports.
5. **Proprietary features** — automatic sensor-based road scoring, offline maps, AI route
   suggestions.

## Architecture

MVVM, feature-based:

```
View → ViewModel → Service → Data Source
```

Coming from React: there's no hooks/context equivalent to reach for. A SwiftUI `View`
is not a component with hooks — state lives in the `ViewModel`, data access lives in a
`Service`, and the `Model` is a plain `struct`. Don't recreate React patterns (heavy
hooks usage, global context-as-store); use small, focused services and protocols for
abstraction/testing instead.

## Package layout

```
Sources/
  SharedModels/          Road, Coordinate, SurfaceType, RoadScore — no dependencies
  OSMClient/             Overpass API client → depends on SharedModels
  RoadScoring/           road quality scoring engine → depends on SharedModels
  CamperEngine/          camper POIs, amenity filtering → depends on SharedModels
  HistoricalRoutes/      Baltic Way waypoints/dataset → depends on SharedModels
  MapFeature/            map screen (View + ViewModel) → depends on SharedModels (once it needs Road data)
  BalticRoadAtlasCLI/    CLI entry point wiring the above together
  BalticRoadAtlasPreview/  macOS window that hosts Feature views for manual
                           verification without Xcode (see "Previewing" below)
Tests/
  <Target>Tests/         one test target per library target

BalticRoadAtlasApp/      real iOS app target, separate from the SPM package above
  project.yml            source of truth — edit this, not the .xcodeproj directly
  BalticRoadAtlasApp.xcodeproj/  generated by `xcodegen generate`, committed for
                                 convenience but disposable
  BalticRoadAtlasApp/     app entry point (@main), imports Feature libraries as a
                          local Swift package dependency on this repo
```

Keep `SharedModels` dependency-free — every other module depends on it, so pulling in
networking or scoring logic there creates cycles. New domain logic goes in its own
target under `Sources/`, mirroring an existing one, with a matching `Tests/*Tests`
target — don't grow `BalticRoadAtlasCLI` into a dumping ground for logic that belongs
in a library target.

Feature libraries (`MapFeature` and whatever follows it — RoadScore, Camper, Reports,
HistoricalRoutes, Search, Settings) live under `Sources/` in the SPM package, each its
own SwiftUI-capable target following View → ViewModel → Service → Model.
`BalticRoadAtlasApp` (the real iOS app target) imports these directly and composes
them (tab bar, cross-feature navigation) rather than owning their internals — new
screens are new Feature libraries under `Sources/`, not new folders inside
`BalticRoadAtlasApp/`. `Core/`, `Shared/`, `Networking/`, `Database/` would follow
standard iOS-app conventions inside `BalticRoadAtlasApp/` for genuinely
app-shell-only concerns (app entry point, cross-feature navigation) if/when they're
needed — nothing there yet.

## Previewing without Xcode

Even with Xcode available, the macOS preview path is still worth using for fast
iteration — no Simulator boot time. SwiftUI and MapKit both work as plain macOS code
(see "Current phase" above). `BalticRoadAtlasPreview` is a throwaway executable target
that hosts one Feature view in a phone-shaped, resizable window:
`swift run BalticRoadAtlasPreview`. When adding a new Feature view, wire it into
`BalticRoadAtlasPreviewApp.swift` instead of building a new preview host each time.
This only proves the view builds and lays out correctly on macOS — always also check
the real thing via `BalticRoadAtlasApp` on the Simulator before calling a feature done
(no iOS chrome, no touch gestures, no on-device quirks on the macOS preview).

## Conventions

- **Models are `struct`s**, `Codable` + `Sendable` where they cross module or async
  boundaries (see `SharedModels`).
- **Swift 6 strict concurrency** is on (`swift-tools-version: 6.0`) — new types that
  cross task boundaries need to be `Sendable` or explicitly isolated; don't silence
  concurrency warnings without understanding why they fired.
- **Tests use Swift Testing** (`import Testing`, `@Test`, `#expect`), not XCTest —
  match the existing test files' style.
- **Networking** is native `URLSession` (see `OSMClient/OverpassClient.swift`) — no
  networking libraries.
- Favor protocols at module boundaries only where there's an actual second
  implementation or test double planned (e.g. a mock Overpass client for tests) — not
  speculatively.

## Commands

```bash
# SPM package (Sources/, Tests/) — library logic, no Simulator needed
swift build                          # build all targets
swift test                           # run all tests
swift run BalticRoadAtlasCLI         # run the CLI smoke test
swift run BalticRoadAtlasPreview     # macOS window preview, no Simulator boot needed
swiftlint lint                       # lint (rules in .swiftlint.yml)
swiftlint lint --fix                 # autocorrect what SwiftLint can fix

# Real iOS app (BalticRoadAtlasApp/) — after editing project.yml
cd BalticRoadAtlasApp && xcodegen generate   # regenerate the .xcodeproj
open BalticRoadAtlasApp/BalticRoadAtlasApp.xcodeproj   # open in Xcode, then Cmd+R
```

Bare `swiftlint` (no wrapper script) works fine now that full Xcode is installed and
selected (`xcode-select -p`) — it wasn't always: on Command Line Tools alone,
SwiftLint can't find `sourcekitd` and crashes. If this ever regresses (e.g. Xcode
gets deselected), that's the symptom to look for.
